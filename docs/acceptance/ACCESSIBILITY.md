# Accessibility acceptance

## Built-in components

- [ ] Native semantic elements are used before ARIA.
- [ ] Every control has an accessible name, visible focus, keyboard operation, and exposed state.
- [ ] Forms associate labels, help, required state, and errors.
- [ ] Dialog-like, tab, expander, toast, progress, and status patterns follow documented keyboard and announcement behavior.
- [ ] Lazy and error regions expose busy and retry states.
- [ ] Data tables, DataEditor, charts, code, JSON, uploads, and downloads have dedicated contracts.

## Visual and responsive

- [ ] Reference themes meet WCAG 2.2 AA contrast where applicable.
- [ ] Zoom, reflow, reduced motion, forced colors, touch targets, and color-independent meaning are tested.
- [ ] HTMX swaps preserve logical focus and announcements.

## Verification

- [ ] Static compiler checks, browser axe-style checks, keyboard scenarios, and screen-reader spot checks are all used.
- [ ] Explorer reports known issues without claiming automated proof of accessibility.
- [ ] Waivers contain rationale, affected users, and remediation plan.
